# Stage 1 — RipelineCore Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the `RipelineCore` Swift package: plan generation, the session state machine with actual-time recording, the lag indicator, the plan-vs-actual comparison, and timeline data, all fully tested.

**Architecture:** Value types only. `PlanGenerator` is a pure function. Session data lives in one `Codable` struct, `SessionSnapshot` (plan + actuals + state). Its internal transition methods take an explicit `now`. `SessionEngine` is a thin public wrapper that reads `now` from an injected `WallClock`, catches up expired segments, and then applies the action. `ScheduleStatus`, `DayComparison` and `Timeline` are pure read models computed from `(snapshot, now)`.

**Tech Stack:** Swift 6.2+ (toolchain installed: 6.4), SwiftPM, Swift Testing, Foundation, Synchronization (test clock only).

**Spec:** [`SPEC.md`](../../SPEC.md), section 4.

**Note on format:** you asked to approve the plan before any code is written, so this plan pins **public interfaces and exact test cases** (inputs → expected outputs) rather than full implementation bodies. Each task runs TDD: write the listed tests, see them fail, implement, see them pass, commit.

## Decisions where the spec is silent (please confirm)

Each decision gets recorded in the SPEC "Decisions log" in the task that implements it.

| # | Topic | Decision |
|---|-------|----------|
| D1 | Naming | `Settings` → **`SessionSettings`** (clashes with SwiftUI's `Settings` scene in the app target). The clock protocol is **`WallClock`** (avoids clashing with Swift's `Clock` protocol). The spec's states enum is `SessionState`. The full persisted state is `SessionSnapshot`. |
| D2 | Units | Inputs stay in `Int` minutes as specced (preset, focus, `minMinutes`, `extend`). All computed durations are `TimeInterval` (seconds); the UI formats them. |
| D3 | Invalid input | `PlanGenerator.generate` **throws `PlanError`** for non-positive preset values, `end <= start`, `focusMinutes <= 0`, `afterWorkBlock(n < 1)`, and `minMinutes < 1`. A valid but too-short day returns `[]`. |
| D4 | Long-break junction | A junction's time is the end of the work block before it, measured on the nominal layout (full blocks, short breaks). Candidates are tried closest-first (earlier wins a tie). If placing the long break pushes out the block after it (so the junction no longer exists), the next candidate is tried. If no candidate fits, the plan has no long break. `.afterWorkBlock(n)` past the last junction → no long break. |
| D5 | Long break + remainder | With `.shortBlock`, if the remainder block sits right after the long-break junction, the long break is used there (the long break replaces the short one). |
| D6 | Day shorter than one block | `.shortBlock(min)` → one block filling the whole window if it is ≥ `min`, otherwise `[]`. `.leaveFree` → `[]`. `.stretchBlocks` → `[]` (no full block to stretch). |
| D7 | Stretch rounding | Extra time is spread in **whole minutes**, with the earliest blocks getting the extra minute first. Any sub-minute residue (only possible with non-minute-aligned input) goes to the last block. The long-break junction is chosen *before* stretching, so stretching may move the long break later. |
| D8 | `.netFocus` | `remainderStrategy` is ignored. |
| D9 | Manual moves | `start` is valid only in `idle` and starts segment 0. `skip` and `advance` **start the next segment immediately**. Auto-advance flags only decide what happens when time runs out. |
| D10 | Which flag applies | Chosen by the kind of the segment that is ending: work → `autoAdvanceWorkToBreak`; any break → `autoAdvanceBreakToWork`. The last segment (always work) with the flag on → `finished`. With the flag off → overtime, and `advance` → `finished`. |
| D11 | Pause / extend scope | `pause` is valid only in `running` (not in overtime: use `advance` or `extend`). `extend` is valid in `running`, `paused` and `overtime`; from overtime it returns to `running` with `endsAt = now + minutes`. |
| D12 | Statuses | Skip from running/paused → `.skipped` (recorded intervals are kept). `skip` in overtime behaves like `advance` → `.completed`. `endDay` while running/paused → current segment `.skipped`; while in overtime → `.completed`. Untouched segments stay `.notStarted`. |
| D13 | `startDay` scope | Valid only in `idle` or `finished`. A day in progress must be ended first. |
| D14 | Interval recording | Every state change closes the open interval and opens a new one (one interval per stretch of running, paused or overtime). Zero-length intervals are dropped. The timeline does the merging. |
| D15 | Clock going backwards | The engine uses `max(clock.now, last recorded instant)`, so it never produces negative intervals. |
| D16 | Comparison | `delta = (work + rest + untracked) − planned`, i.e. wall-clock overrun. `actualEnd` = end of the last recorded interval once `finished`, `nil` before that. Planned end of day = end of the last planned segment. |
| D17 | Lag when finished | `projectedEnd = actualEnd`. `ScheduleStatus` is `nil` for an empty plan, or when the day finished with nothing recorded. |
| D18 | Small additions | `updateSettings(_:)` (applies to future transitions only; an open pause interval keeps its kind). `isAllowed(_:)` so the UI can enable/disable buttons. `remainingTime()` and `overtimeElapsed()` for the countdown. `Timeline.bounds` for the shared axis. |

## Review Focus

1. **Clock moves backwards** (manual time change, NTP correction) between actions → no negative or reordered intervals; `tick()` with an earlier `now` is a no-op. *Test in Task 5.*
2. **Restore long after persist** (app relaunched hours later with a `running` snapshot) → the first `tick()` catches up exactly as if the app had been asleep. *Test in Task 9.*
3. **Non-minute-aligned start** (user starts the plan at 09:03:27) → the generator and stretch still end exactly at `end`. *Test in Task 2.*
4. **Two actions at the same instant** (pause + resume, or start + skip, at the same `now`) → no zero-length intervals. *Test in Task 3.*
5. **Read models before `startDay` / on an empty plan** → no crash; `ScheduleStatus` is `nil`, comparison and timeline are empty. *Tests in Tasks 6–8.*

Internal design:
- `workDurations(for request, longBreakAfter: Int?) -> [TimeInterval]` computes the work block lengths.
  - `.untilTime`: greedy. Add a full block while `t + breakBefore + W <= end`, where `breakBefore` is 0 for the first block, L after junction `longBreakAfter`, S otherwise. Then apply the remainder strategy.
  - `.netFocus`: `ceil(F / W)` blocks, the last one being `F − (n−1)·W`.
- `layout(start, durations, longBreakAfter) -> [PlannedSegment]` lays the blocks out contiguously with breaks between them, no trailing break, and indices `0..<n`.

### Task 5: Segment expiry — overtime, auto-advance, extend, skip, advance

**Files:**
- Modify: `Session/SessionSnapshot+Transitions.swift`, `Session/SessionEngine.swift`
- Create: `Tests/.../SegmentExpiryTests.swift`

**Interfaces — Consumes:** Task 4. **Produces:** the `extend` / `skip` / `advance` bodies, and `catchUp(to:)` handling a single expiry plus the loop (Task 6 adds the multi-segment tests).

Expiry rule, inside `catchUp`, looping while `running(i, endsAt)` and `endsAt <= now`: close the open interval at `endsAt`. If the flag for `plan[i].kind` is on (D10): mark `completed`, then start `i+1` at `endsAt`, or `finished` if `i` is last. Otherwise: `overtime(i, since: endsAt)` with an open interval of the segment's kind from `endsAt`.

| From \ Action | extend(m) | skip | advance |
|---|---|---|---|
| running | endsAt += m | seg skipped → next running at now / finished | ✗ |
| paused | remaining += m | seg skipped → next running at now / finished | ✗ |
| overtime | → running(i, now+m) | = advance | seg completed → next running at now / finished |
| idle, finished | ✗ | ✗ | ✗ |

`extend(minutes <= 0)` throws `.nonPositiveExtension`.
